# Myron WCN786x no-opening-reset experiment

Status: hardware diagnostic attempted once; discovery not yet qualified.

The existing userspace firmware/NVM loader and patched QCA IBS attachment
publish a powered BlueZ controller, but device discovery is not reliable. A
known discoverable JBL speaker produced no UI device, and the controller timed
out LE scan opcodes. Reference raw-UART runs isolate the boundary: repeated
version commands pass before HCI Reset and stop receiving responses after it,
despite acknowledged IBS wake and a held UART clock vote.

`0003-bluetooth-qca-skip-open-reset.patch` sets the existing
`HCI_QUIRK_RESET_ON_CLOSE` before `hci_register_dev()` only when the non-serdev
`qca_preinitialized` opt-in is active. It also exposes the normal QCA public-
address callback and leaves this path unconfigured until the stage programs
the address parsed from exact NVM tag 2. It does not alter normal QCA
controllers.

This is a one-shot diagnostic, not a production fix. Closing the HCI device
still sends Reset and may require the existing guarded `btpower` cleanup before
another attach. Acceptance requires:

1. Exact Android GKI source revision
   `5a0e85dd9db068df8f0cdff9be76fe4211bd8af9` and existing patches 0001/0002.
2. Exact-release `hci_uart.ko`; all unrelated module hashes unchanged.
3. Fresh coexistence-profile boot with ModemManager and GNSS absent.
4. NVM public-address programming followed by fresh known-peer discovery via
   `myron-bluetooth-stage scan EXPECTED-PEER`, not only scan exit zero.
5. Bounded cleanup, controller power-off, rollback disarm and a fresh-boot retry.

Pairing, reconnect and Bluetooth audio remain separate later gates.

## First hardware attempt (2026-10-26)

The exact candidate booted and reported kernel-notes SHA-256
`dadfc0372f028cd5c9810415167af6c182e79fbf2954e7c555a8a1108cf33e1e`.
The loader acknowledged all 1211 ELF and 60 NVM segments.  The kernel logged
`preinitialized controller; skipping opening HCI Reset`, registered `hci0`,
enabled the QCA IBS transport and exposed management API 1.23.  BlueZ then
reported `No Bluetooth address for index 0` before the test runner detached
the controller about 5.6 seconds after registration.

BlueZ cannot recover from an all-zero address merely by waiting longer. The
next candidate marks the controller unconfigured, installs QCA's existing
`set_bdaddr` callback and programs the address parsed at runtime from the exact
hash-pinned NVM before BlueZ starts. The address is neither logged nor stored
in this repository. A zero-event scan now fails qualification.

Two packaging defects found before the controller test are also fixed: the
generated POSIX `case` selector now parses, and the candidate-aware prepare
script is included in composed images. The proprietary Bluetooth firmware is
accepted only from an explicit private input directory, copied into the
private payload, and never committed. Runtime code no longer mounts or reads
Android slot B.

The watchdog remained armed because discovery did not qualify.  Cleanup
stopped BlueZ, detached `hci0`, powered off the controller and left automatic
slot-A-only rollback responsible for restoring both boot images.

Because Android GKI protects exports from its signed module set, rebuilding
only `hci_uart.ko` is insufficient: a fresh build uses a fresh autogenerated
module key. The test therefore pairs the rebuilt kernel `Image` with all seven
modules from the same build. `compose-payload.sh` accepts only the
exact reviewed v14b coexistence image and exact hash-pinned build outputs.
`tools/myron-build-test-init-boot` must be given both the candidate and rollback
`boot_a` images so its independent watchdog restores `boot_a` before
`init_boot_a`. Neither path names or touches slot B.

`0ecd0f4eb2f6ab7c073ef2f2afd94e4185ac404b2b01a04a666188d63f029db8`,

`build-boot.py` accepts only the exact postmarketOS slot-A rollback image and
the exact kernel above. It preserves the reviewed header-v4 and AVB metadata,
uses an explicitly unsigned hash footer, reads the kernel back, and never
contacts the phone. `compose-payload.sh` requires the two proprietary firmware
files through `--firmware-dir`; their expected hashes are public provenance,
but the files remain under `out/private/` and are never committed.

Hardware qualification remains pending. The candidate waits for the
unconfigured MGMT index, programs the NVM public address, then verifies the
configured MGMT index without logging the identity. Its Bluetooth-only boot
loads only the exact `smem-mailbox.ko` and `cnss_utils.ko` prerequisites already
packaged in the payload. It masks the radio foundation, leaves Wi-Fi and modem
remote processors stopped, never reads slot B, keeps AudioReach and
ModemManager stopped, and prevents the graphical qualifier from disarming
rollback. BlueZ state is mounted on a private bounded tmpfs and the diagnostic
journal is volatile, so discovered identities do not enter the payload
filesystem. Pass requires a fresh bounded event from the named peer, clean
controller power-off, and automatic postmarketOS rollback if any gate fails.

## First powered discovery result (v44, 2026-10-26)

The exact v44 candidate completed firmware loading, public-address setup and
BlueZ publication. A bounded 20-second BR/EDR scan then failed closed because
Inquiry Cancel (`0x0402`) returned `-16` and BlueZ remained in
`Discovering: yes`. Controller cleanup repeated that error before the guarded
power cut. The 900-second watchdog restored the exact postmarketOS `boot_a`
and `init_boot_a` hashes; slot B was not read or written.

The next diagnostic stops the first 10.24-second Classic inquiry at seven
seconds instead of spanning multiple inquiry intervals. Patch 0004 also lets a
later Inquiry Complete finish a stuck management stop without interrupting an
active LE scan. That recovery logs an identity-free kernel warning. The stage
waits at most 15 seconds, records only fresh expected-peer count, Inquiry
Cancel failure count, recovery count and monotonic timestamps, and still
requires `Discovering: no`, a fresh peer, zero cancel failures, zero recovery,
bounded power-off and exact rollback disarm.
Raw `bluetoothctl` output is discarded so peer names and addresses never enter
the persistent diagnostic log.
